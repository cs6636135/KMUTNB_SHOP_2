การวิเคราะห์ผล: สิ่งที่ยังขาดและควรทดสอบเพิ่มเติม (Future Test Analysis)

แม้ว่าระบบผ่านการทดสอบระดับ Unit & Integration Test ครบ 11 เคสหลักแล้ว จากการวิเคราะห์ตามหลักวิศวกรรมซอฟต์แวร์ ยังมีแง่มุมที่ควรวางแผนทดสอบเพิ่มเติมในอนาคต ดังนี้:

1. การทดสอบ Concurrency และ Race Condition ขั้นสูง

แม้ในโค้ดจะใช้ select_for_update() เพื่อล็อกแถวใน Database แล้ว แต่ควรทดสอบ Load Test ด้วยเครื่องมือเช่น Locust หรือ JMeter โดยยิงคำขอจอง 100 requests พร้อมกันในเสี้ยววินาทีเดียวเพื่อพิสูจน์ว่าจะไม่เกิด Stock ติดลบในสภาพแวดล้อมที่มี High Concurrency

2. การทดสอบ Brute Force และ Rate Limiting บนรหัสการจอง

ควรเพิ่ม Rate Limiting ในหน้าค้นหาสถานะ /status/ เพื่อป้องกันกรณีผู้ไม่หวังดีสุ่มเลขรหัสนักศึกษาหรือรหัสการจองอย่างต่อเนื่อง

3. End-to-End Browser UI & Network Latency Test

การทดสอบการตอบสนองของ HTMX เมื่อเครือข่ายมือถือของนักศึกษาช้า (Slow 3G Simulation) ว่ามี Skeleton Loading และ Indicator แสดงผลอย่างสวยงามและไม่เกิดสถานะหลงเหลือบน DOM

4. การทดสอบ Background Worker สำหรับ Expire Job

ปัจจุบันระบบคืน Stock อัตโนมัติเมื่อมีการเรียกดูข้อมูล (Event-driven) ในระดับ Production ควรทดสอบร่วมกับ Celery Beat หรือ Crontab ที่รันเป็นรอบเวลา Background สม่ำเสมอ

การทบทวนและประเมินโครงงาน (Evaluation & Reflection)

1. โค้ดนี้ทำอะไร?

ระบบ KMUTNB Shop พัฒนาขึ้นเพื่อแก้ปัญหานักศึกษาและบุคลากรไม่ทราบว่าสินค้าประจำมหาวิทยาลัย (เช่น เสื้อช็อป, เข็มมงกุฎ, ตำราเรียน) มีจำหน่ายที่อาคารใดและเหลือจำนวนเท่าใด โดยระบบช่วยให้นักศึกษาสามารถค้นหาสินค้า ดูสต็อกแยกตามจุดจำหน่าย (เช่น อาคาร 40, อาคาร 81, ศูนย์หนังสือ) และทำการจองออนไลน์ล่วงหน้าได้ โดยระบบจะล็อกสต็อกและสร้างรหัสการจองที่มีอายุ 4 ชั่วโมง ให้นักศึกษานำรหัสไปรับและชำระเงินที่เคาน์เตอร์จริง หากเกิน 4 ชั่วโมงระบบจะตัดเป็น Expired และคืนของเข้าสต็อกอัตโนมัติ สำหรับส่วนหลังบ้าน ระบบแบ่งสิทธิ์ชัดเจนระหว่าง Admin (จัดการได้ทุกสาขา) และ Staff (จัดการได้เฉพาะสาขาตนเอง)

2. ทำไมเลือกวิธีนี้? (Django + HTMX + Tailwind)

  • Django ORM + Atomic Transactions: ใช้ transaction.atomic() และ select_for_update() เพื่อรับประกันความถูกต้องของ Stock แบบ ACID ป้องกันการจองชนกัน (Race Condition) ได้ 100%
  • Django Built-in Security: ปกป้องระบบด้วย CSRF Tokens, Safe Session Cookies, SQL Injection Prevention ผ่าน ORM และ Password Hashing (PBKDF2)
  • HTMX: ช่วยให้หน้าค้นหาสินค้า และเช็คสถานะการจองอัปเดตผลลัพธ์ได้ทันทีโดยไม่ต้อง Refresh หน้าเว็บ ทำให้ UX ลื่นไหลเหมือน SPA แต่ไม่ต้องเสีย Overhead ในการสร้าง Client-side SPA ซับซ้อน
  • Tailwind CSS (CDN): ช่วยสร้างธีม UI สีแดงหมากสุก มจพ. (KMUTNB Vermillion) ได้อย่างประณีต รองรับทั้ง Mobile-first สำหรับนักศึกษา และ Desktop Dashboard สำหรับเจ้าหน้าที่

3. ข้อจำกัดของระบบ (ตามระบุในเอกสารโครงการ)

  1. ระบบไม่ได้เชื่อมต่อกับระบบทะเบียนนักศึกษามหาวิทยาลัยจริง จึงยังไม่สามารถตรวจสอบความถูกต้องของรหัสนักศึกษากับฐานข้อมูลกลางได้โดยตรง
  2. ระบบไม่ได้เชื่อมต่อกับ Payment Gateway และไม่รองรับการชำระเงินออนไลน์ ผู้ใช้ต้องชำระเงินที่จุดจำหน่ายจริง (เงินสดหรือ QR หน้าร้าน)
  3. ระบบไม่ได้เชื่อมต่อกับเครื่อง POS/ระบบคลังสินค้าภายนอกของแต่ละร้าน ข้อมูลสต็อกขึ้นอยู่กับการบันทึกของ Admin และ Staff ในระบบนี้
  4. ระบบไม่มีการเชื่อมต่อกับระบบขนส่งพัสดุ เนื่องจากเน้นให้ผู้ใช้เดินทางมารับที่จุดจำหน่ายด้วยตนเอง
  5. ระบบออกแบบสำหรับขนาดโครงการระดับการศึกษา จึงยังไม่ได้ออกแบบเพื่อรองรับผู้ใช้งานพร้อมกันในระดับ Production ขนาดใหญ่ (เช่น จัดคลัสเตอร์)
  6. การจองใช้รหัสนักศึกษาเป็นข้อมูลระบุตัวตน ยังไม่มีระบบยืนยันตัวตนขั้นสอง เช่น SMS OTP หรือ KMUTNB Single Sign-On (SSO)

4. ถ้าเกิด bug จะแก้อย่างไร?

มีกระบวนการแก้ไขอย่างเป็นระบบ: (1) ตรวจสอบ Logs ผ่าน Django Debug Server และ Test logs, (2) เขียน Regression Unit Test ใน reservations/tests.py เพื่อจำลองสถานการณ์ที่เกิดบั๊กนั้นให้ Failure ก่อน, (3) ตรวจสอบ Database Integrity หากเกิดจาก Stock ผิดพลาดสามารถตรวจสอบย้อนหลังได้จากตาราง Reservation และ Product_locations, (4) แก้ไขโค้ดใน Service Layer หรือ View และรันชุดทดสอบซ้ำจนกระทั่งผลลัพธ์ผ่าน 100%
